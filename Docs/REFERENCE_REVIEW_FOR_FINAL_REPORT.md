## 표절 방지 원칙

- 레퍼런스에서 가져오는 것은 **구성 방식(목차 흐름, 슬라이드 배분, 시연 구성)과 좋은 패턴**뿐이다.
- **문장, 이미지, 코드, 표를 그대로 복사하지 않는다.** 요약/메모도 원문 인용이 아니라 구조 설명으로만 남긴다.

### 참고 가능한 요소
- 목차/섹션 순서와 비중 (예: 개요 → 기획 → 구현 → 시연 → 회고)
- 슬라이드 수 배분, 한 슬라이드당 정보 밀도
- 스크린샷/영상 배치 방식, 캡션 스타일
- 시스템 설명 다이어그램의 추상화 수준
- 트러블슈팅/회고 섹션을 다루는 방식
- 데모 흐름(플레이 순서) 소개 방식

### 참고하면 안 되는 요소
- 문장 표현 그대로 복사 (한 문장이라도 금지)
- 타 팀 게임의 스크린샷/아트/로고
- 코드 블록, 표 데이터의 그대로 이식
- 타 팀 고유의 기획 콘텐츠(스토리/캐릭터 설정)를 변형 없이 차용

## 좋은 레퍼런스 공통 패턴

1. 제안서 대비 최종 구현 비교가 강하다. 7.pptx처럼 기존 계획과 최종 결과를 나란히 놓으면 변경 이유와 달성도가 한눈에 보인다.
2. 기능 설명은 코드 원문보다 기능 단위 표가 좋다. 29.pptx, 34.pptx, 44번 보고서처럼 화면/입력/상태/함수/결과로 나누면 읽기 쉽다.
3. 시연은 스토리보드처럼 단계화한다. 36.pptx처럼 플레이 흐름을 화면 순서로 쌓으면 발표자가 말을 잃지 않는다.
4. 핵심 메커닉은 초반에 바로 보여준다. 17.pptx의 거울 메커닉, 46번의 레이저 반사처럼 MR3D도 기억 렌즈를 초반 대표 이미지로 보여줘야 한다.
5. 실패/한계는 감추지 말고 개선 방향과 묶는다. 26.docx, 35.pptx처럼 미구현/부족한 점을 다음 작업으로 연결하면 평가자가 납득하기 쉽다.
6. 스크린샷은 장식이 아니라 증거로 쓴다. 시작, 핵심 조작, 성공/실패, 결과 화면을 순서대로 배치해야 한다.

## Memory Recycler 3D에 적용할 보고서 작성 전략

- 보고서는 게임 소개보다 “왜 이 게임이 기억 렌즈 게임인지”를 먼저 설득한다. 폐도시 복원 게임처럼 시작하지만, 실제로는 플레이어의 선택까지 수집/재활용한다는 반전을 중심축으로 둔다.
- 구현 설명은 `씬/데이터/매니저/UI/월드 UI/아카이브/플레이어 기록` 단위로 나눈다. 코드 원문은 최소화하고, 클래스 책임과 호출 흐름을 표와 다이어그램으로 설명한다.
- 발표 안정화 작업도 결과물로 다룬다. 플레이어 접지, UI 가독성, 엔딩 조건, 처리 완료 3개 제한처럼 실제 시연을 막는 문제를 어떻게 줄였는지 짧게 기록한다.
- 테스트 결과는 “성공/실패 여부”보다 QA 루프 중심으로 쓴다. 기억 구체 회수, LensAlign, LensOcclude, Stillness, 선택 처리, 아카이브 심문, 엔딩 진입을 체크리스트로 정리한다.
- 한계점은 약점이 아니라 다음 개발 계획으로 연결한다. 전체 8개 기억 중 특수 렌즈 퍼즐이 3개에 집중된 이유와 확장 방향을 명확히 쓴다.

## 표절 방지 주의사항

- 레퍼런스의 문장, 표, 코드, 이미지, 로고, 스크린샷은 그대로 복사하지 않는다.
- 참고 대상은 목차 흐름, 정보 배치, 발표 순서, 기능 설명 방식으로 한정한다.
- OpenGL 자료의 함수명/코드 설명은 MR3D의 Unity/C# 클래스 책임 설명으로 재해석한다.
- 과목 핵심 자료의 표지/목차 틀도 그대로 베끼지 말고 MR3D의 콘셉트와 구현 내용에 맞게 재구성한다.
